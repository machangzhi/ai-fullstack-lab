# Week 4 Day 5：测试与评估

> 目标：把「这个 Prompt 好像变好了」变成可复现的数据结论。用 Mock 模型响应测试评测逻辑，用 20 条固定测试集衡量真实模型，并比较两套 Prompt 的准确率、成功率与延迟。

## 一、单元测试与模型评测的分工

这两件事经常被混在一起，但解决的问题不同：

| 维度     | 单元测试                         | 模型评测                             |
| -------- | -------------------------------- | ------------------------------------ |
| 验证对象 | 代码逻辑是否正确                 | Prompt 与模型组合的效果是否达标      |
| 输入     | 固定输入 + Mock 响应             | 固定测试集 + 真实模型                |
| 结果     | 确定：通过或不通过               | 概率性：同一输入也可能得到不同结果   |
| 成本     | 毫秒级、零费用                   | 每次调用真实计费，受网络与限流影响   |
| 运行时机 | 每次提交、CI                     | 改 Prompt、换模型、发版前            |

因此本日拆成两层：

```text
单元测试层：runChecks / summarizeResults / runVariant（callModel 由测试注入 Mock）
        ↑ 验证评测器本身可信
真实评测层：run.cjs → runVariant（callModel 调用真实模型）→ 报告
        ↑ 用可信的评测器衡量 Prompt
```

如果评测器本身算错了，真实评测跑得再多也没有意义。所以先让评测逻辑离线可测，再花 Token 跑真实模型。

## 三、20 条固定测试集

数据集固定为 20 条，客服与分类各 10 条：

| 模板     | 条数 | 覆盖点                                                         |
| -------- | ---- | -------------------------------------------------------------- |
| support  | 10   | 退款、验证码、发票、越界请求、隐私信息、重复扣款、白屏、封禁申诉、超期退款、写代码 |
| classify | 10   | 五类基础分类、模糊输入、功能建议，以及两个优先级冲突用例       |

两个专门设计的「冲突用例」：

- `classify-damaged-package`：快递盒压扁导致杯子碎了。按关键词既像「物流配送」也像「产品质量」，v2 的判定顺序要求包裹破损优先归物流。
- `classify-mixed-return`：屏幕有裂痕且想退货。v2 规定「退货」优先级最高，应归售后服务，而不是产品质量。

固定测试集的价值在于**可比**：用例、检查规则、温度都不变，指标变化才能归因到 Prompt 本身。随机生成输入看起来覆盖更广，但两次评测的难度不同，结果无法比较。

每条用例都包含：

```json
{
  "id": "support-refund-delay",
  "template": "support",
  "input": "申请退款三天了还没到账……",
  "expected": "必须转人工，且不承诺退款",
  "checks": { "contains": ["转人工"], "notContains": ["保证退款"], "maxChars": 300 }
}
```

`expected` 只写进报告供人阅读；真正的判定仍由 `checks` 完成，避免「期望描述」和「程序判断」两套标准。

## 四、Mock 模型响应：让评测器离线可测

执行器 `runVariant` 不直接 `fetch`，而是接收一个 `callModel` 函数：

```ts
const run = await runVariant({
  variant: { id: 'support-mock', template: 'support' },
  cases,
  systemPrompt: '测试提示词',
  callModel: async ({ caseId }) => {
    if (caseId === 'boom') throw new Error('模拟超时');
    return { content: '需要转人工：退款异常。', model: 'mock-model' };
  },
  now: () => nextTick(), // 注入时钟，延迟断言稳定
});
```

这样做有三个好处：

1. 单元测试不访问网络、不需要密钥，几毫秒完成；
2. 可以精确构造「调用成功但校验失败」「调用直接抛错」等真实模型难以稳定复现的场景；
3. 计时逻辑只有一份，真实调用与 Mock 走同一条执行路径。

测试文件：[evals.test.cjs](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/tests/evals.test.cjs)。覆盖规则校验、分位数、指标汇总、Mock 执行器和数据集完整性。

## 五、指标口径

```text
准确率 accuracy    = 通过规则校验的用例数 / 总用例数
成功率 successRate = 模型调用成功的用例数 / 总用例数
失败率 failureRate = 模型调用失败的用例数 / 总用例数 = 1 - 成功率
```

必须把「答错」和「没答」分开：

- 准确率衡量 Prompt 效果；
- 成功率 / 失败率衡量服务可用性；
- 如果只报一个「通过率」，供应商故障导致的超时会伪装成 Prompt 变差。

延迟统计口径：

- 只统计**调用成功**的用例，包括「调用成功但校验失败」；
- 超时与 HTTP 错误的耗时取决于超时阈值，混入平均值会把网络故障误读成模型变慢；
- 同时给出平均值、P50、P95：平均值容易被少数慢请求拉高，P95 更能反映尾部体验。

P50/P95 使用线性插值，与常见监控系统口径一致。样本只有 10 条时，分位数只能看趋势，不应精确到毫秒做结论。

## 六、真实评测结果

运行时间：2026-11-21；模型：`deepseek-flash`；温度：0.2；4 个版本共 40 次调用。

| 版本        | 通过  | 准确率 | 成功率 | 失败率 | 平均延迟 | P50   | P95   | Tokens |
| ----------- | ----- | ------ | ------ | ------ | -------- | ----- | ----- | ------ |
| support-v1  | 10/10 | 100%   | 100%   | 0%     | 1278ms   | 1194ms | 1896ms | 4018   |
| support-v2  | 10/10 | 100%   | 100%   | 0%     | 916ms    | 1012ms | 1247ms | 4473   |
| classify-v1 | 8/10  | 80%    | 100%   | 0%     | 635ms    | 601ms  | 928ms  | 2528   |
| classify-v2 | 10/10 | 100%   | 100%   | 0%     | 523ms    | 543ms  | 629ms  | 4574   |

版本对比：

- **support**：准确率都是 100%；v2 平均延迟从 1278ms 降到 916ms，P95 从 1896ms 降到 1247ms。v2 增加了 250 字上限，单条输出更受约束；但 Prompt 本身更长，总 Tokens 从 4018 增到 4473。
- **classify**：准确率从 80% 提升到 100%，`classify-vague` 与 `classify-mixed-return` 由失败转为通过。代价是 Prompt 变长，Tokens 从 2528 增到 4574（约 +81%）。
- **延迟差异不能单独归因于 Prompt**：同一版本在不同时间运行会有几百毫秒波动，且网络、供应商负载都会影响。本次 v2 更快，只能说明「没有明显变慢」，不能证明「v2 一定更快」。

失败案例分析：

| 用例                    | v1 输出类别 | 期望     | 原因                                                   |
| ----------------------- | ----------- | -------- | ------------------------------------------------------ |
| `classify-vague`        | 产品质量    | 其他     | 信息不足时倾向猜测；v2 增加置信度标准后选择「其他」    |
| `classify-mixed-return` | 产品质量    | 售后服务 | v1 没有优先级规则；v2 明确「退货」优先于「商品质量」   |

## 九、已知限制

- **单次运行**：模型输出仍非确定，温度 0.2 也不能保证完全一致。严格结论应重复 3 次取中位数或看分布。
- **样本小**：每个模板 10 条，只适合发现明显回归，不足以代表全部线上流量。
- **规则校验的边界**：关键词检查可能被同义表达漏判，也可能被「恰好包含关键词」误判；它衡量的是可观察约束，不是语义质量。
- **v1 是历史副本**：测试保证生产模板与 `-v2.txt` 逐字一致，但 `-v1.txt` 只是历史快照，不保证与当时的线上版本完全一致。
- **延迟受环境影响**：网络、地区、供应商负载都会造成波动；脚本没有做多次采样与预热。
- **失败率只表示调用失败**：HTTP 200 但内容为空、结构错误的响应会计入准确率失败，而不是失败率。
- **没有成本核算与 CI 门槛**：目前只统计 Tokens，没有按单价折算费用，也没有「准确率低于阈值则阻断发布」的流水线。

## 十、自测题

1. 为什么要把准确率和成功率分开统计？
2. 为什么延迟统计要排除调用失败的用例？
3. 单元测试里为什么注入 `callModel`，而不是 Mock 全局 `fetch`？
4. 为什么用 20 条固定用例，而不是每次随机生成输入？
5. classify-v2 准确率更高但 Tokens 更多，应该怎样决定是否切换？

### 参考答案

1. 两者描述不同问题：准确率衡量 Prompt 是否让模型答对，成功率衡量服务是否可用。合并成一个指标时，供应商超时会被误判为 Prompt 变差，排查方向就错了。
2. 失败请求的耗时由超时阈值决定，例如固定 45 秒超时，它反映的是故障而不是模型速度。把它算进平均延迟，会让「网络故障」看起来像「模型变慢」。失败调用仍然单独记录耗时，便于排查。
3. `fetch` 是全局依赖，Mock 它需要拦截网络层、构造 HTTP 细节，测试脆弱且与实现耦合。注入 `callModel` 后，测试直接表达「模型返回什么 / 抛什么错」，执行器逻辑仍然完整执行。
4. 固定用例保证两次评测难度一致，指标变化才能归因到 Prompt。随机输入每次难度不同，无法判断提升来自 Prompt 还是运气。
5. 先看准确率提升是否覆盖关键场景（本次修复了两个分类错误），再评估成本增量与业务价值。如果分类调用量大、Tokens 成本敏感，可以只对歧义输入使用 v2，或压缩 v2 的示例与规则，重新评测后再决定。
