# Week 4 Day 4：可靠性

> 目标：模型调用不再「一次失败就整体失败」。为所有 AI 调用加上超时、有限重试、并发限制与熔断，并把失败收敛成稳定的错误码。

## 一、为什么模型调用需要可靠性层

模型调用和普通数据库查询有三个关键差异：

1. **慢**：一次请求可能持续数秒到数十秒，连接占用远高于普通接口；
2. **贵**：每次重试都会真实计费，不能像内部 RPC 那样无限重试；
3. **外部不可控**：供应商限流、超时、区域性故障都无法在业务代码里修复。

如果业务层直接 `await transport.complete()`，任何一次网络抖动都会变成用户看到的 500。可靠性层的职责就是把这些不稳定因素挡在业务代码之外：

```text
业务层（AiService / ToolChatService / ConversationChatService）
        ↓ 只认识 ChatTransport
ReliableChatTransport：并发闸门 → 熔断 → 超时 → 有限重试
        ↓
LlmService：按模型档案路由
        ↓
OpenAiChatTransport：OpenAI 兼容协议
```

包装层实现同一个 `ChatTransport` 接口，所以业务层完全不需要改动调用方式。实现：[reliable-chat.transport.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/reliable-chat.transport.ts)

## 二、超时：给每一次尝试设上限

实现：[reliable-chat.transport.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/reliable-chat.transport.ts)

每次尝试都有独立的时间预算（默认 30 秒）：

```text
AbortController
  ├─ 定时器到点 → abort → 标记 timedOut → 抛 AiCallTimeoutError
  └─ 上层取消   → abort → 保留原错误（客户端断开不算故障）
```

两个容易混淆的概念：

| 情况               | 处理方式                     |
| ------------------ | ---------------------------- |
| 服务端超时预算耗尽 | `AI_TIMEOUT`（504），可重试  |
| 用户关页面 / 断网  | 直接结束，不重试、不计入熔断 |

超时信号会一路透传到 OpenAI SDK 的 `signal` 参数，真正取消上游请求，而不是只丢弃结果。否则请求仍在供应商侧继续执行、继续计费。

**流式调用例外**：流式只透传取消信号，不做整段超时。长回答本身可能超过 30 秒，按整段计时会误杀正常请求；连接超时由 SDK 负责，客户端断开由 AbortController 负责。

## 三、有限重试：只重试值得重试的错误

实现：[retry.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/retry.ts)、[reliability-errors.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/reliability-errors.ts)

### 3.1 错误分类

| 可重试                       | 不可重试                          |
| ---------------------------- | --------------------------------- |
| 单次调用超时                 | 模型档案配置缺失（503 配置错误）  |
| 网络不可达 / 连接中断        | 客户端传了不存在的模型别名（400） |
| 供应商 429 限流              | 供应商 401/403 鉴权失败           |
| 供应商 5xx                   | 请求参数错误（400/422）           |
| 空回复（可能是下游偶发抖动） | 业务层的 `AppError`               |

对不可重试错误重试只会重复失败、重复计费，还会把一次明确的配置问题拖成 30 秒超时。

### 3.2 指数退避 + 抖动

```text
等待时间 = min(retryMax, retryBase × 2^(attempt-1)) × rand(0.5, 1)
```

- **指数**：供应商越忙，退避越久，避免持续加压；
- **抖动**：把多个客户端原本同频的重试打散，避免同一秒再次形成尖峰；
- **上限**：避免指数无限增长导致请求挂起过久。

默认 `maxAttempts=3`：首次 + 最多两次重试。重试期间仍然占用并发槽位，保证「在途请求」数量始终受控。

## 四、并发限制：信号量

实现：[semaphore.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/semaphore.ts)

```text
active < capacity  → 立即获得槽位
active = capacity  → 进入 FIFO 队列
等待超过 queueTimeoutMs → 抛 AiConcurrencyLimitError（AI_CONCURRENCY_LIMIT）
release()          → 直接把槽位转交给下一个等待者
```

设计细节：

1. **槽位转让而不是先减后加**：避免释放瞬间被新请求插队，等待者顺序更公平；
2. **release 幂等**：重复调用不会把计数减成负数；
3. **队列有超时**：容量满时不让请求无限排队，宁可快速失败也不让用户等到连接超时。

注意区分两种「限流」：

- 本层的**并发限制**保护的是「同时占用多少资源」，属于服务端自保；
- Week 2 的**登录限流**是按用户/时间窗计数，属于安全策略。

两者互补，不能互相替代。

## 五、熔断：避免持续撞一个坏供应商

实现：[circuit-breaker.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/reliability/circuit-breaker.ts)

```text
closed ──连续失败达到阈值──► open
  ▲                            │
  │                       冷却期结束
  │                            ▼
  └────探测成功──────── half-open
                               │
                          探测失败 → 重新 open
```

关键规则：

1. **按逻辑请求计数**，而不是按重试次数。一次请求重试 3 次仍失败只记 1 次，否则阈值会被单次请求瞬间打满；
2. **只有可重试的上游失败才计数**。400/401 是客户端或配置问题，不应该让整个供应商熔断；
3. **按模型档案独立熔断**。一个供应商故障不应拖垮另一个可用模型；
4. **半开只放一个探测请求**，成功恢复、失败重新打开，避免恢复瞬间被流量冲垮；
5. 探测请求因排队超时或被取消时，要归还探测名额，否则该档案会永远停在 half-open。

熔断打开时直接返回 `AI_CIRCUIT_OPEN`，不再等待一次必然失败的 30 秒超时。

## 六、幂等：重试前必须想清楚的问题

重试的前提是「重复执行不会产生额外副作用」。当前链路的安全边界：

| 操作                     | 是否可安全重试 | 原因                                       |
| ------------------------ | -------------- | ------------------------------------------ |
| 普通对话 / 结构化输出    | 可以           | 只读，最多多花一次 Token                   |
| 历史摘要                 | 可以           | 结果覆盖写，失败由上层降级                 |
| 工具调用（当前两个工具） | 可以           | `get_current_time` / `calculator` 无副作用 |
| 未来的退款、删除、发消息 | **不可以**     | 重试可能重复执行                           |

因此本层只对**无副作用调用**做自动重试。以后接入有副作用的工具时，必须由业务层生成幂等键（例如 `requestId + toolCallId`），让下游按幂等键去重，而不是依赖「重试一次应该没事」。

## 七、统一错误码

映射位置：[ai.service.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/ai.service.ts)

| 场景               | HTTP | 错误码                 | 前端处理建议           |
| ------------------ | ---- | ---------------------- | ---------------------- |
| 单次调用超时       | 504  | `AI_TIMEOUT`           | 提示稍后重试           |
| 并发饱和、排队超时 | 503  | `AI_CONCURRENCY_LIMIT` | 稍后重试，可加退避     |
| 熔断打开           | 503  | `AI_CIRCUIT_OPEN`      | 稍后重试，或切换模型   |
| 供应商 429         | 429  | `RATE_LIMITED`         | 遵循现有限流约定       |
| 网络不可达         | 503  | `AI_UNAVAILABLE`       | 提示检查网络           |
| 鉴权失败           | 502  | `AI_PROVIDER_AUTH`     | 服务端配置问题，不重试 |
| 其他供应商异常     | 502  | `AI_PROVIDER_ERROR`    | 通用兜底               |

所有错误信息都不包含供应商原始响应、地址或密钥。重试耗尽后抛出的是最后一次的原始错误，由 `AiService` 统一映射，避免在两层各维护一套错误码。

## 十、已知限制

- 并发限制与熔断都是**进程内存实现**，多实例部署时每个实例各自计数；跨实例需要 Redis 或网关层统一限流。
- 熔断状态在重启后清零，冷启动瞬间可能把已经恢复的故障再探测一遍。
- 流式调用不重试；如果上游在首个 delta 之前就失败，用户需要重新发起请求。
- 重试只覆盖非流式路径，工具调用按「每轮一个逻辑请求」重试，轮次上限仍是 4。
- 幂等目前只是约束（只重试无副作用调用），还没有幂等键基础设施。
- 没有把并发、熔断状态暴露成监控指标；线上需要配合日志与 Week 6 的观测能力。

## 十一、自测题

1. 为什么 400 和 401 不应该自动重试？
2. 为什么熔断按「逻辑请求」计数，而不是按「每次尝试」计数？
3. 流式调用为什么不做重试和整段超时？
4. 并发槽位已经在排队了，为什么还要给排队设超时？
5. 半开状态为什么要限制「同时只允许一个探测请求」？

### 参考答案

1. 这两类错误由请求本身或服务端配置决定，重试不会改变结果，只会重复失败、增加延迟和费用。401 还可能因为连续失败触发供应商的风控。
2. 一次请求自带最多 3 次尝试，如果按尝试计数，阈值 5 会被两次失败请求直接打满，熔断过于敏感。按逻辑请求计数才符合「这个供应商最近是否稳定」的语义。
3. 流已经向前端输出了部分文本，重试会拼接出重复内容；长回答本身就可能超过固定的整段预算，整段计时会误杀正常请求。取消与超时分别交给客户端信号和 SDK 连接超时。
4. 没有排队超时，容量满时请求会一直挂着，直到客户端或网关超时。快速失败能让用户更早得到可理解的错误，也能避免请求在队列里堆积占用内存。
5. 供应商刚恢复时可能仍然不稳定；如果同时放大量流量，会把刚恢复的服务再次打垮。单探测请求相当于一次低成本的健康检查。

## 十二、今日三行

- 今天解决了什么问题：用装饰器方式给所有模型调用加上单次超时、有限指数退避重试、全局并发限制和按档案熔断，并把失败统一成 `AI_TIMEOUT` / `AI_CONCURRENCY_LIMIT` / `AI_CIRCUIT_OPEN`。
- 为什么这样设计：包装层实现同一个 `ChatTransport` 接口，业务代码零改动；只重试可重试错误和无副作用调用；熔断按逻辑请求计数。
- 还有什么不确定：多实例下的全局并发与熔断、真实供应商 429/5xx 的恢复表现、有副作用工具的幂等键设计，留到后续迭代。
