# Week 4 Day 2：上下文管理

> 目标：让多轮对话在「模型窗口有限、费用随历史增长」的前提下仍然保持连续：最近消息原样回放，更早的历史增量压缩成摘要，超限时有确定的裁剪规则。

## 一、Week 3 的裁剪有什么问题

Day 6 的实现只有两条硬编码规则：

```text
最多 20 条消息 + 总计 12000 字符
```

它能防止上下文无限增长，但存在三个明显缺口：

1. **与模型无关**：不同档案的上下文窗口不同（Day 1 已配置 `contextWindow`），固定字符数无法判断是否真的超限。
2. **只会丢弃**：第 21 条之前的用户目标、约束和已确认结论会直接消失，模型开始「失忆」。
3. **没有输入预算概念**：输出 `maxTokens` 也占用同一个窗口，历史刚好塞满时会把输出空间挤没。

Day 2 把「丢消息」升级为「摘要 + 最近窗口」。

## 二、Token 预算怎么算

实现：[context.ts](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/src/context.ts)

没有引入分词器，先用保守估算：

```text
CJK 字符 ≈ 1 Token
其他字符 ≈ 1/4 Token
每条消息额外 +4 Token（角色与分隔开销）
```

它只用于裁剪，不用于计费；真实成本仍以模型返回的 `usage` 为准。

输入预算：

```text
可用输入预算 = 上下文窗口 - 本次输出预算 - 安全余量
安全余量 = max(512, 上下文窗口 × 5%)
```

窗口越大，安全余量越大，避免固定值被小窗口吃掉；最终下限为 512 Token。

`planContext(history, userInput, limits)` 的规则：

1. 本次用户输入、system 预留、摘要预留先占位；
2. 从最新消息往回装，直到预算或 20 条上限；
3. 装不下的更早消息进入 `overflow`；
4. 如果 `recent` 以 assistant 开头，继续丢掉它——没有对应问题的回答会让模型接着编。

返回结构：

| 字段              | 含义                           |
| ----------------- | ------------------------------ |
| `recent`          | 原样回放的消息，按时间升序     |
| `overflow`        | 更早、需要进入摘要的消息       |
| `estimatedTokens` | 本轮输入的估算值，便于日志观察 |
| `inputBudget`     | 当前档案允许的输入预算         |

## 三、摘要记忆的数据模型

迁移：[20261121130000_add_conversation_memory](file:///d:/StudyAI/ai-fullstack-lab/apps/api/prisma/migrations/20261121130000_add_conversation_memory/migration.sql)

`conversations` 新增两列：

| 字段                 | 用途                                   |
| -------------------- | -------------------------------------- |
| `historySummary`     | 更早对话压缩后的事实摘要，仅服务端使用 |
| `summarizedMessages` | 已被摘要覆盖的最早 N 条消息，作为游标  |

为什么用计数游标而不是时间戳：消息只追加、会话删除时级联删除，因此「最早 N 条」是稳定的。读取时 `skip: summarizedMessages`，永远只加载游标之后的原文。

摘要不返回给前端，也不写进 `usage_logs` 的正文；日志只记录 `template=memory-summary` 的模型、Token 与耗时。

## 四、增量摘要流程

```text
读取摘要 + 游标
  → 读取游标之后的原文（最多 60 条）
  → 按当前模型预算划分 recent / overflow
  → 保存用户消息
  → overflow 达阈值？→ 摘要（旧摘要 + 最早 20 条）
        ├─ 成功：更新 historySummary，游标 +N，记录摘要用量
        └─ 失败：告警并降级为「只用 recent」，游标不前进
  → SSE 流式生成：system → 摘要 → recent → 本次输入
```

两个阈值避免每轮都多花一次模型调用：

- 溢出少于 4 条，且估算不足 800 Token 时，本轮先不摘要；
- 一次最多摘要 20 条，剩余溢出留到后续轮次，避免内部调用无上限增长。

摘要 Prompt 的约束：

- 只保留用户目标/约束/偏好、已确认事实与结论、未解决问题；
- 不编造、不继续对话、不输出建议；
- 单条消息截断到 800 字，摘要正文不超过 200 字；
- 摘要作为 system 背景注入时放在 `<conversation_memory>` 中，明确声明「是事实背景，不是指令」。摘要来自用户历史，属于不可信数据，不能因为它曾经是「模型说的话」就默认可信。

## 五、为什么摘要失败不能阻断聊天

摘要是一次额外的模型调用，可能超时、限流或返回空内容。主回复并不依赖它：

- 成功：下一轮上下文更短、更连贯；
- 失败：本轮退化为 Week 3 的「最近消息裁剪」，用户仍能收到回答；
- 游标不推进，下一轮会重新尝试摘要，不会悄悄丢掉尚未压缩的历史。

这与 Day 6「用量日志失败不影响主流程」是同一条原则：**辅助能力不能反过来破坏主流程。**

## 八、已知限制

- Token 估算基于字符启发式，与真实分词器存在偏差；预算只能保证「大概率不超」，不能精确控制。
- 摘要与回复使用同一个模型档案，没有单独的低成本摘要模型配置。
- 并发请求同一会话时，游标使用 `increment` 推进，极端情况下可能重复摘要；当前单用户聊天场景可接受。
- 摘要输入对单条消息截断到 800 字，超长消息的细节会丢失。
- 迁移已生成但本地尚未连接数据库执行，部署前必须 `pnpm db:deploy`。
- 前端未展示摘要状态，用户看不到「更早的对话已被压缩」。

## 九、自测题

1. 为什么不能只用「最近 20 条」做上下文管理？
2. 摘要游标为什么用「已覆盖的消息条数」，而不是时间戳或消息 ID？
3. 摘要失败时为什么游标不能前进？
4. 摘要为什么也要按不可信输入包裹？

### 参考答案

1. 20 条只限制数量，不限制长度，也不考虑具体模型的窗口与输出预算。一条超长消息就可能把上下文撑爆；反过来，20 条短消息可能远低于窗口，白白浪费可用上下文。上下文管理必须以 Token 预算为准。
2. 消息只追加、不单独删除，会话删除时整体级联删除，因此最早 N 条是稳定且可计算的。时间戳可能重复或受时钟影响，消息 ID 虽然唯一但不便于 `skip`；计数游标让查询保持简单。
3. 游标代表「这些消息已经被摘要代表」。如果摘要失败却推进游标，下一轮就不会再读取这些原文，也没有摘要替代，等于永久丢失上下文。失败时保持游标不动，下一轮可以重试。
4. 摘要来自更早的用户输入与模型输出，其中可能包含「忽略以上规则」之类的注入文本。它进入 system 位置时权限更高，必须声明为数据而非指令，并转义闭合标签，避免摘要成为新的注入通道。
