## 一、Token：模型处理文本的基本单位

Token 不等于字符，也不等于单词。模型会按照训练时确定的词表，把文本切分成 Token：

- 英文常见单词可能对应一个 Token，也可能被拆成多个子词。
- 中文汉字、标点、空格和换行的切分结果取决于具体模型的分词器。
- 不同模型的分词结果不能直接互相套用。

因此，按字符数估算 Token 只能用于早期粗略预算，不能用于精确计费。实际项目应优先读取模型响应中的 `usage`，需要提前计算时再使用对应模型的官方分词器。

## 二、上下文窗口与最大输出 Token

一次对话请求占用的上下文可以简化为：

```text
system 提示词 + 对话历史 + 当前用户输入 + 工具结果 + 模型输出
    ≤ 模型上下文窗口
```

`MODEL_MAX_TOKENS` 限制的是**本次生成的输出预算**，不是模型能够接收的对话历史长度。

例如，模型上下文窗口为 128K、`maxTokens=2048` 时，输入历史可以远大于 2048 Token，但输入和输出总量仍不能超过 128K。实际可用输入预算通常需要为本次输出预留空间：

```text
可用输入预算 ≈ 上下文窗口 - 本次输出预算 - 安全余量
```

这就是后续需要历史截断、最近 N 轮消息和超长历史摘要的原因。

## 三、温度与采样

模型生成文本时，会根据候选 Token 的概率分布逐步采样。温度会调整这个分布：

| 温度倾向 | 输出特点               | 常见适用场景               |
| -------- | ---------------------- | -------------------------- |
| 较低     | 分布更集中，输出更稳定 | 分类、信息抽取、结构化输出 |
| 较高     | 分布更分散，输出更多样 | 头脑风暴、创意写作         |

需要注意：

1. 温度影响的是随机性，不直接等于准确率。
2. 温度低不代表 Prompt 设计、权限校验和输出校验可以省略。
3. 即使温度为 0，也不应假设不同模型版本、服务商或运行环境永远产生逐字一致的结果。
4. `top_p` 等参数也参与采样，但本日配置只覆盖温度，避免一次引入过多旋钮。

## 四、模型输入、输出与费用估算

输入不仅是用户当前发送的一句话，还可能包含 system 提示词、历史消息、RAG 上下文和工具结果。输出也不仅是最终展示文本，部分模型还会单独统计推理 Token 或缓存 Token。

基础费用估算公式为：

```text
费用 = 输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价
```

如果供应商提供缓存、推理等独立计费项，需要按账单规则分别计算。估算可用于预算控制，实际结算应以模型响应的用量数据和供应商账单为准。

## 五、为什么需要 ModelProvider 配置层

业务层关心的是“调用哪个模型、使用什么采样参数”，不应该在每个 Controller 中重复读取环境变量、拼接地址或判断供应商。

本日在 `packages/ai-core` 中实现：

- `resolveModelProviderConfig`：读取并校验环境变量，生成服务端内部完整配置。
- `toPublicModelProviderConfig`：通过白名单生成可公开配置，排除密钥和连接地址。
- 配置解析是纯函数，可注入环境对象进行测试，不读取真实 `.env`、不访问网络。
- Day 2 将复用这份配置创建模型客户端；Week 4 再扩展统一 LLMService 和 Provider 调用抽象。

### 两种供应商的配置策略

| 配置项           | openai-compatible | deepseek                                   |
| ---------------- | ----------------- | ------------------------------------------ |
| `MODEL_BASE_URL` | 必须显式填写      | 默认 `https://api.deepseek.com/v1`，可覆盖 |
| `MODEL_NAME`     | 必须显式填写      | 默认 `deepseek-chat`，可覆盖               |
| `MODEL_API_KEY`  | 必填              | 必填                                       |

`openai-compatible` 只描述协议兼容，不代表某一家具体供应商。随意设置默认地址可能把密钥发送到错误或不可信的服务，因此必须显式配置。DeepSeek 的供应商明确，可以提供官方默认值。

### 数值与安全校验

| 环境变量            | 默认值       | 校验规则                                  |
| ------------------- | ------------ | ----------------------------------------- |
| `MODEL_TEMPERATURE` | `0.7`        | 数值范围为 0～2                           |
| `MODEL_MAX_TOKENS`  | `2048`       | 正整数                                    |
| `MODEL_TIMEOUT_MS`  | `30000`      | 正整数                                    |
| `MODEL_BASE_URL`    | 无通用默认值 | 仅允许 HTTP(S)，不允许 URL 中携带账号密码 |

错误信息只包含环境变量名称，不输出变量值，避免密钥进入异常日志。

## 六、公开配置为什么使用白名单

完整配置只能留在服务端内部。返回浏览器前，当前只保留：

- `provider`
- `model`
- `temperature`
- `maxTokens`

不仅 `apiKey` 不能公开，`baseUrl` 也可能暴露内网地址，`timeoutMs` 则属于客户端无需了解的运维细节。

白名单比“复制完整对象后删除 `apiKey`”更安全：以后新增代理密码、签名密钥等字段时，不会因为忘记删除而意外泄露。核心原则是：**默认不公开，只返回明确允许公开的字段。**

## 八、自测题与参考答案

### 1. 为什么 `MODEL_MAX_TOKENS=2048` 不代表模型只能接收 2048 Token 的对话历史？

因为它限制的是**本次模型生成的输出 Token 数**，不是输入长度。

假设模型上下文窗口为 128K，本次请求大致满足：

```text
系统提示词 + 对话历史 + 当前输入 + 模型输出 ≤ 128K
```

`maxTokens=2048` 只是给输出预留最多 2048 Token。输入历史可以远大于 2048，但输入与输出总量仍不能超过上下文窗口，因此后续需要历史裁剪和摘要策略。

### 2. 为什么 OpenAI 兼容模式必须显式填写 `MODEL_BASE_URL`，而 DeepSeek 可以使用默认值？

“OpenAI 兼容”只说明**接口协议兼容**，不代表某一家具体供应商。DeepSeek、通义、本地 vLLM、企业代理都可能提供兼容接口，它们的地址和密钥并不通用。

如果随意设置默认地址，可能把 API Key 发送到错误甚至不可信的服务。因此：

- `openai-compatible`：必须明确指定 `MODEL_BASE_URL` 和 `MODEL_NAME`。
- `deepseek`：供应商明确，可以安全地提供官方默认地址和模型，同时允许覆盖。

### 3. 为什么公开配置采用白名单，而不是简单地删除 `apiKey` 字段？

白名单更安全，也更稳定：

- `baseUrl` 可能暴露内网地址，本身也可能敏感。
- 以后新增 `proxyPassword`、签名密钥等字段时，容易忘记删除。
- 直接删除字段可能只处理当前层级，遗漏嵌套敏感数据。
- 白名单明确规定“客户端可以知道什么”，新增字段默认不会泄露。

核心原则是：**默认不公开，只返回明确允许公开的字段。**
