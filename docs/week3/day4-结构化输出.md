# Week 3 Day 4：结构化输出

> 目标：让模型输出从「看起来像 JSON」变成「经过校验、可以安全交给程序使用」的数据。

## 一、今天要解决的问题

Day 3 的分类模板已经要求模型输出 JSON，但代码只是把文本原样返回。这意味着：

- 模型加了 Markdown 围栏、前后解释，前端就 `JSON.parse` 失败。
- 字段名写错、`confidence` 超出 0~1、类别不在枚举里，程序仍然照收。
- 失败后要么直接报错，要么盲目重发同一条提示词，得到同样的错误结果。

Day 4 把这层补上：**JSON Schema 定义契约，Zod 执行校验，失败只安全重试一次。**

## 二、JSON Schema 与 Zod 的关系

|          | JSON Schema              | Zod                          |
| -------- | ------------------------ | ---------------------------- |
| 本质     | 描述 JSON 结构的标准格式 | TypeScript 里的运行时校验库  |
| 用途     | 跨语言、跨服务约定接口   | 应用内部校验 + 类型推导      |
| 类型来源 | 需要另外生成 TS 类型     | `z.infer` 直接从 schema 推导 |
| 失败信息 | 标准但偏底层             | 带字段路径，适合定位         |

本项目选择 Zod，因为它同时解决「运行时校验」和「编译期类型」两件事，不用维护两份定义。

核心原则：**模型输出是外部输入，和用户提交的表单、第三方接口返回同级，必须校验。**

## 三、两套 schema

文件：[parse.ts](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/src/structured/parse.ts)

### 3.1 反馈分类

```ts
z.object({
  category: z.enum(['产品质量', '物流配送', '售后服务', '账号与支付', '其他']),
  confidence: z.number().min(0).max(1),
  reason: z.string().trim().min(1).max(40),
}).strict();
```

`.strict()` 的作用是拒绝未声明字段。没有它，模型多返回一个 `sentiment` 也会被静默接受，契约就松了。

### 3.2 实体抽取

```ts
z.object({
  entities: z
    .array(
      z
        .object({
          type: z.enum(['人物', '组织', '产品', '时间', '金额', '其他']),
          value: z.string().trim().min(1).max(100),
        })
        .strict(),
    )
    .max(20),
}).strict();
```

这里特意保留了「其他」类型。真实测试中「北京」被归入「其他」，说明枚举少了 `地点` 会损失信息——这是设计取舍，不是模型错误。

## 四、解析策略：先降噪，再校验

模型常见的「格式噪声」有三种：代码围栏、前后解释、空内容。解析器按顺序处理：

````text
原始文本
  → 去掉 ```json ... ``` 围栏
  → 截取第一个 { 到最后一个 }
  → JSON.parse
  → schema.safeParse
  → 成功返回数据 / 失败返回稳定原因
````

失败被归为三类，方便上层决定是否值得重试：

| reason            | 含义                           | 是否值得重试           |
| ----------------- | ------------------------------ | ---------------------- |
| `empty`           | 模型返回空内容                 | 值得                   |
| `invalid_json`    | 解析不出 JSON                  | 值得                   |
| `schema_mismatch` | 能解析，但字段/类型/范围不符合 | 值得，但要带上具体原因 |

注意：解析器**不做业务修正**。例如 `confidence: 1.5` 不会被自动截断成 `1`，因为静默修正会让错误数据流进下游，比直接失败更危险。

## 五、一次安全重试

实现位置：[ai.service.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/ai/ai.service.ts)

### 5.1 重试为什么不能原样重发

同一段提示词 + 同一段输入，大概率得到同样的错误输出。所以第二次请求把失败原因写回用户消息：

```text
上一次输出无法解析：字段 confidence 不符合约定：Number must be less than or equal to 1。
请只输出符合要求的 JSON，不要 Markdown 代码块，不要解释。
```

### 5.2 为什么只重试一次

- 费用：每次重试都是完整的一次模型调用，Token 重新计费。
- 延迟：单次可能接近 30 秒超时，重试越多用户等待越久。
- 收敛：连续两次失败通常说明提示词或 schema 本身有问题，继续重试只是浪费额度。

因此 `STRUCTURED_MAX_ATTEMPTS = 2`，两次都失败返回 **502 `AI_INVALID_OUTPUT`**。

### 5.3 用量要累计

响应中的 `usage` 是**所有尝试的总和**，`attempts` 记录真实请求次数。只报最后一次会低估成本，尤其在重试率高的场景。

## 九、自测题

1. 既然提示词已经要求「只输出 JSON」，为什么还需要 Zod 校验？
2. 重试时为什么不直接把原来的用户消息再发一次？
3. 为什么解析器不把 `confidence: 1.5` 自动修正为 `1`？

### 参考答案

1. 提示词是「请求」，不是「保证」。模型可能加代码围栏、少字段、类型错误或超出枚举；而且提示词本身也可能被注入影响。Zod 在代码层给出确定性的边界：不合格就不进入业务逻辑，避免脏数据写库或触发下游异常。
2. 相同的输入和提示词通常产生相同的错误输出，原样重发只是在消耗额度。把「上次失败的具体原因」写回消息，相当于给模型一次有针对性的修复机会，成功率更高。
3. 自动修正会掩盖两类问题：模型理解错误，以及 schema 设计过松。静默把 1.5 改成 1，数据看起来正常，但语义已经不可信；直接失败能让问题暴露在日志和测试里，由人决定是改提示词还是改契约。
