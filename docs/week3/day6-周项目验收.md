## 二、现状盘点与缺口

## 三、多轮上下文怎么组装

文件：[templates.ts](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/src/prompts/templates.ts)

模板新增 `systemPrompt` 字段，并把消息组装拆成两步：

```text
system（模板固定）
+ 历史 user / assistant
+ 本次 user（<user_input> 包裹）
```

三条约束：

1. **条数上限 20 条**：上下文越长越贵，也越容易被旧内容干扰。
2. **字符上限 12000**：粗粒度 Token 预算保护；超限从最旧的消息开始丢弃。
3. **不能以 assistant 开头**：丢掉了问题却留下答案，模型会对着没有上下文的回答继续编。

历史中的用户内容同样做闭合标签转义，避免历史回放时重新激活注入文本。

## 四、落库时机与事务

文件：[conversation-chat.service.ts](file:///d:/StudyAI/ai-fullstack-lab/apps/api/src/modules/conversations/conversation-chat.service.ts)

```text
归属校验
  → 读取历史
  → 保存用户消息
  → 调用模型并逐段转发
  → 保存助手消息 + 更新会话时间/标题（同一事务）
  → 写入用量日志（旁路，失败不影响主流程）
```

几个刻意的取舍：

- **用户消息先落库**：模型失败或用户中断时，提问仍然保留，刷新后能看到自己发过什么。
- **助手消息后落库**：只保存完整回复，半截回答进入历史会污染下一轮上下文。
- **用量日志独立写入**：统计是辅助能力，不能因为日志表故障把已经生成的回复丢掉。
- **标题只生成一次**：会话仍是「新对话」时取首条用户消息前 20 字，之后不再自动改名。

## 九、已知限制

- 会话暂不支持重命名和删除；标题只用截断生成，没有额外调用模型。
- 中断生成不保存半截回复，也不回滚已保存的用户消息。
- `today` 按服务器本地时区的 0 点统计，多时区部署需要改为按用户时区或 UTC。
- 历史只按条数与字符裁剪，没有精确的 Token 计数。

## 十、自测题

1. 为什么用户消息要在调用模型之前落库，而助手消息要等流结束再落库？
2. 历史为什么要同时限制条数和字符数？
3. 用量日志写入失败为什么不应该让整个请求失败？

### 参考答案

1. 用户消息先落库，保证模型失败或用户主动停止时提问不会丢，刷新后仍能看到会话内容；助手消息后落库，是为了只保存完整回复，避免半截内容进入下一轮上下文造成误导。
2. 只限条数无法防止超长消息把上下文撑爆，只限字符数又可能保留大量碎片消息。两者结合，既控制成本，也保证语义连续性。
3. 回复已经生成并保存，主流程已经完成。日志是旁路观测数据，为了统计去回滚用户可见的结果，等于让辅助系统破坏主流程。正确做法是记录告警、继续返回结果。
