# Week 3 Day 7：Prompt 调优实践

> 目标：用可重复的评测代替「感觉好像变好了」，并通过版本对比决定哪套 Prompt 进入生产。

## 一、为什么需要评测

Day 3 的模板和 Day 5 的问答应答都能跑通，但「能回答」不等于「回答稳定」。调 Prompt 时常见三个问题：

1. 改了一句话，不知道整体变好还是变坏。
2. 只测自己想到的那一个例子，边界输入立刻翻车。
3. 版本改来改去，最后说不清线上用的是哪一版。

所以这次先建评测，再谈优化。

版本记录放在 [evals/prompts](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/evals/prompts)：

| 文件              | 内容                                 |
| ----------------- | ------------------------------------ |
| `support-v1.txt`  | Day 3 上线版本                       |
| `support-v2.txt`  | 增加范围拒绝、人工升级、250 字上限   |
| `classify-v1.txt` | Day 3 上线版本                       |
| `classify-v2.txt` | 增加判定优先级、置信度标准与五类示例 |

## 三、评测集

数据集：[prompt-baseline.json](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/evals/datasets/prompt-baseline.json)

9 个用例，覆盖三类最容易出问题的地方：

- **业务正确性**：退款争议必须转人工；发票问题必须提到发票。
- **安全边界**：用户主动发送身份证号、银行卡号时必须劝阻；不能反向索要。
- **范围与模糊输入**：要求写诗时必须拒绝；「东西不太好」这种信息不足的反馈应归入「其他」。

评分全部是确定性规则，不引入裁判模型：

| 检查                       | 含义                                                |
| -------------------------- | --------------------------------------------------- |
| `contains` / `containsAny` | 必须出现的关键词                                    |
| `notContains`              | 禁止出现的承诺或敏感内容                            |
| `maxChars`                 | 输出长度上限                                        |
| `json`                     | 复用生产解析器校验 JSON、枚举、置信度和 reason 长度 |

## 四、运行方式

```bash
pnpm --filter @ai-lab/ai-core eval:prompts
# 只跑某一版
node packages/ai-core/evals/run.cjs --variant classify-v2
```

脚本 [run.cjs](file:///d:/StudyAI/ai-fullstack-lab/packages/ai-core/evals/run.cjs) 的取舍：

- 用生产的 `buildPromptMessages` 组装消息，保证 `<user_input>` 包裹与注入防护和线上一致。
- 温度固定 0.2，评测要可复现，不沿用会话的 0.7。
- 非流式调用，只看最终文本。
- 报告写入 `evals/reports/` 并加入 `.gitignore`，避免把每次调优的临时产物提交进仓库。

## 五、评测结果（真实 DeepSeek 调用）

18 次调用，耗时约 25 秒，合计 7213 Tokens。

| 版本        | 通过 | 通过率 | 平均耗时 | 平均字数 | 总 Tokens |
| ----------- | ---- | ------ | -------- | -------- | --------- |
| support-v1  | 5/5  | 100%   | 1535ms   | 178      | 2083      |
| support-v2  | 5/5  | 100%   | 1115ms   | 106      | 2292      |
| classify-v1 | 3/4  | 75%    | 1263ms   | 69       | 1011      |
| classify-v2 | 4/4  | 100%   | 1488ms   | 60       | 1827      |

### 分类模板：明确提升

失败用例是「东西不太好，不太满意」：

- v1 判成「产品质量」，理由把模糊描述当成了质量问题。
- v2 依据「判定顺序 + 置信度标准」，判成「其他」，置信度 0.35，理由说明缺少具体问题。

这是真实业务风险：错误分类会把无效工单直接派给质量团队。

### 客服模板：通过率饱和，但输出质量更好

两版都通过 5/5，说明 Day 3 的模板本身没有硬伤。差异体现在三处：

- 平均字数 178 → 106，v1 的输出接近 300 字上限，v2 按 250 字约束更紧凑。
- 超范围请求：v1 拒绝后仍追加两条无关步骤并触发「需要转人工」；v2 只用一句话拒绝，不制造假工单。
- 退款争议：v1 给出较多自助步骤后才转人工；v2 直接要求订单号并转人工，符合「退款一律人工」的业务规则。

## 六、结论与回写

- **classify 采用 v2**：通过率从 75% 提升到 100%，有明确证据。
- **support 采用 v2**：通过率无变化，但输出更短、超范围请求更干净；理由来自规则外的输出审查，已如实记录，不夸大为「评测提升」。

两版 v2 已回写生产模板，并用一致性测试锁定。

## 七、已知局限

- 评测集只有 9 个用例，规则是手写的，存在过拟合风险；新增业务规则时应先补用例再改 Prompt。
- 全部为确定性检查，无法评价「语气是否自然」这类主观质量。
- 没有多次采样。模型有随机性，单次通过的结论可能不稳定；下一步应对失败用例重复采样。
- 结果显示模型为 `deepseek-flash`，与配置的 `deepseek-chat` 别名不同，成本对比只能作相对参考。
- 客服模板通过率已饱和，区分度不足；后续应增加更细的约束（例如「超范围回答不超过 60 字」）。

## 八、自测题

1. 为什么评测脚本要复用生产的消息组装函数，而不是自己拼 system + user？
2. 客服两版通过率相同，为什么仍然选择 v2？这样做有什么风险？
3. 如果某个用例第一次通过、第二次失败，评测结果应该怎么处理？

### 参考答案

1. 评测的目的是预测线上表现。如果自己拼消息，评测通过但生产仍可能因包裹方式、注入防护不同而表现不一致，评测结论就失去意义。
2. 通过率相同不代表质量相同：v2 输出更短、范围拒绝更干净，符合产品规则。风险是这些判断来自人工阅读而非自动检查，带有主观性；应补充可量化的检查项，避免「凭感觉采纳」。
3. 单次结果不可靠，应固定温度并重复采样，记录通过率而不是通过/失败二值；对不稳定的用例单独标记，优先修复 Prompt 而不是反复重跑碰运气。

## 九、今日三行

- 今天解决了什么问题：建立可重复的 Prompt 评测，发现分类模板对模糊输入的系统性错误，并用 v2 修复。
